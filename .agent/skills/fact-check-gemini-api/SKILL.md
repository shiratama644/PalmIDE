# Skill: Gemini API ファクトチェック

Gemini の課金・API形状・提供状況を本文に書き込むときの、**「推測を断定化しない」**ための手順（R5 レビューの教訓）。

## いつ使うか

- `RATE_TABLE` の値を更新するとき
- 新しい API メソッド名を仕様に書くとき
- 「GA 日付」や「サービス終了日」に言及するとき

## 優先順位（情報源の階層）

1. **公式**: `ai.google.dev` / `ai.google.dev/gemini-api/docs/*` / 公式ブログ
2. **一次情報**: GitHub の公式リポジトリ（`google-gemini/*` 等）
3. **補助**: 第三者記事（公式確認の**補助**にのみ使用。単独で「確認済み」と書かない）

## 手順

1. Web検索で最も具体的なクエリを投げる（例: `Gemini 3.7 Flash context caching pricing site:ai.google.dev`）
2. **少なくとも2つの公式ページ**で同じ値を確認する（例: pricing と caching の両方）
3. 第三者サイトの数値と公式を**照合**し、矛盾があれば公式を採用して脚注で矛盾を記録
4. 値を仕様に書き込む場合は、**「確認日・ソースURL」**を括弧内か脚注に残す
5. 検証結果を人間に報告する（Rule 04 の形式）。値だけ暗黙に直さない

## 禁止パターン（R5 で指摘された例）

- 「×倍」「割引率は○○」を公式確認なしで式に埋め込む
- 第三者ブログ1件だけを根拠に「確認済み」と書く
- 公式が見つかってもリンクを残さず「よくわからないが約○○」と書く
